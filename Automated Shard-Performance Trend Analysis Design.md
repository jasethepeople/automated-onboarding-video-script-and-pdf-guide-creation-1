# Automated Shard-Performance Trend Analysis Design

The trend-monitoring extension analyzes only the merged, non-secret shard metrics generated by the protected workflow. It retains a bounded run history, compares the latest run with recent **successful** baseline runs, and records performance signals without reading test artifacts that may contain screenshots, logs, browser state, or other sensitive content.

## Storage options

| Approach | Data location | Advantages | Trade-offs |
|---|---|---|---|
| **Protected `metrics-history` branch** | A versioned JSON file in the same private repository | No external service; reviewable history; dashboard-ready file; straightforward retention. | Requires a narrowly scoped `contents: write` job on protected `main`. |
| External object store / analytics database | Organization-approved cloud storage | Better retention, query capability, and multi-repository aggregation. | Requires an OIDC integration, cloud policy, and additional setup. |
| GitHub artifact history only | Per-workflow-run artifacts | No repository write permission. | Difficult to aggregate across runs; artifact expiration limits trend visibility. |

The package implements the **protected `metrics-history` branch** approach because it keeps the initial system self-contained. The history job runs only after protected `main` runs and uses only the merged dashboard-metrics artifact produced by the same workflow. The `contents: write` permission is scoped to that job alone. If your organization already has governed analytics storage, replace this branch publisher with an OIDC-backed uploader rather than adding another long-lived credential.

## Baseline and thresholds

| Signal | Baseline | Default detection rule | Interpretation |
|---|---|---|---|
| Matrix wall-clock duration | Median of the previous 10 successful runs, minimum 5 | Latest duration is ≥20% slower **and** at least 30 seconds slower | The complete shard matrix has slowed materially. |
| Shard imbalance | Median imbalance across same baseline | Latest imbalance is ≥15 percentage points higher **and** exceeds 35% | One shard is disproportionately slower than its peers. |
| Retry count | Median retries across baseline | Latest retries ≥ baseline + 2 and ≥2 total | Flakiness or session/browser instability increased. |
| Test failure | Latest run status | Latest run is not successful | A functional failure; it is recorded separately from a performance regression. |

> A median baseline reduces the influence of isolated slow runs. The analyzer requires five previous successful observations before it raises performance-regression signals; fewer observations are recorded as **insufficient baseline**, not treated as healthy performance.

## Retention and safe data boundary

The history file retains the newest **60** run summaries. It includes only the dashboard schema’s run/shard timing, status, count, and public run-URL fields. It excludes browser state, cookies, base64 text, headers, traces, screenshots, secret values, and full console logs.

The history publisher should be protected by branch rules and workflow-file code ownership. GitHub recommends limiting workflow credentials to the least privilege necessary and using read-only `GITHUB_TOKEN` permissions by default, increasing permissions only for individual jobs that require a write.[1]

## Output artifacts

Each run produces two safe deliverables:

| Output | Consumer | Contents |
|---|---|---|
| `dashboard-metrics-history.json` | HTML Shard Observatory | Retained multi-run `runs` array, ready for import. |
| `shard-trend-analysis.json` | CI summary, issue alert, and operations review | Current baseline, threshold configuration, signals, and human-readable findings. |
